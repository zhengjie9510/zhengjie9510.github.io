假设你想让 AI 帮你安排下周的日程：工作会议、健身、看牙，还有周末的朋友聚餐。

你先给它接入几个 Tool：查询日历、创建日程、设置提醒。这样，AI 已经能够调用工具，完成一些基本操作。

但很快你发现，**会调用工具，不代表知道怎么把日程安排好**。它不知道你习惯早上做需要专注的工作，也不知道你希望两场会议之间留出休息时间。

于是，你又整理了一套 Skill，把自己的时间偏好、安排原则和每周计划模板交给 AI。

看起来已经差不多了。但当你希望不同的 AI 助手都能使用这套日历工具时，新的问题出现了：不同应用之间，如何共享这些工具？难道每个应用都要重新适配一遍？

这就是 MCP 要解决的问题。

**Tool、Skill、MCP 都能扩展 AI 的能力，但它们并不在同一个层面。**

---

## 🔧 Tool：让 AI 能够调用外部功能

大模型擅长理解和推理，但它并不能凭空查看你的日历、创建日程，或者发送一封邮件。

如果希望 AI 完成这些操作，开发者就需要把相应功能封装成工具，并把工具的名称、用途和参数描述提供给模型。

例如，给 AI 一个查询日程的 Tool：

```python
def get_events(date: str):
    return calendar.get_events(date)
```

当用户说“帮我看看下周一有哪些安排”时，模型可以根据工具描述，决定调用 `get_events`，并把对应日期作为参数。随后由外部程序执行函数，再把结果返回给模型。

这就是 Tool 的基本工作方式。

Tool 的好处是直接、灵活。需要什么功能，就定义什么工具；工具的输入和输出也比较明确，方便调试和控制。

不过，Tool 主要解决的是**功能如何被调用**。至于工具如何注册、如何描述、不同 AI 应用之间如何共享，传统的自定义 Tool 并没有统一的答案。开发者可以通过 API、SDK 等方式实现复用，但仍然需要处理不同应用之间的适配。

> **简单理解：Tool 解决的是 AI 能调用什么功能。**

---

## 📖 Skill：让 AI 知道如何把事情做好

有了 Tool，AI 已经能够查询日历、创建日程、设置提醒。但如果让它安排一周的生活，它是否知道哪些事情应该优先安排？怎样避免排得太满？遇到时间冲突又该怎么办？

这些不是增加几个工具就能解决的。

这时候，Skill 就有了用武之地。

Skill 更像一份专业的操作手册：把某类任务需要的知识、规则和工作流程整理起来，让 AI 在遇到相应任务时按需使用。

例如，一个每周日程规划 Skill 可以包含：

- 个人偏好：早上留给需要专注的工作，晚上安排运动；
- 安排原则：会议之间留出休息时间，外出时预留路程时间；
- 冲突处理：先安排不能改期的事项，有冲突时先询问；
- 输出格式：按天列出安排，标明待确认事项。

在常见的 Agent Skills 实现中，通常以 `SKILL.md` 作为入口文件，也可以附带脚本、参考文档和模板等资源。

它的价值在于**沉淀知识、偏好和工作经验**。同一套安排原则不必每次都写进 Prompt，也不必为每个任务重新组织一遍。

但 Skill 也不是万能的。它主要负责告诉 AI 怎么做，并不天然拥有访问日历的能力。需要查询或创建日程时，仍然要依赖 Tool、API，或通过 MCP 接入的工具。

另外，Skill 中的指令需要模型理解和执行，不能仅凭写好了流程，就保证每一步都一定正确。

> **简单理解：Skill 解决的是 AI 应该如何完成一类任务。**

---

## 🔌 MCP：让不同 AI 应用用统一方式连接外部系统

现在，Tool 负责具体操作，Skill 负责指导操作流程。但还有一个问题：如果多个 AI 应用都要使用同一套外部能力，应该怎么接入？

例如，我们开发了一套日历工具，提供查询空闲时间、创建日程、设置提醒等功能。最初，这些工具只在一个 AI 助手中使用。后来，希望其他支持 MCP 的 AI 应用也能使用它们。

如果每个应用都采用不同的接入方式，就需要分别开发适配逻辑。

MCP（Model Context Protocol，模型上下文协议）提供了另一种思路：**让能力提供方和 AI 应用遵循同一套交互协议。**

可以把 MCP 类比成 USB-C。USB-C 不负责实现鼠标、键盘或显示器的功能，它提供的是一套统一的连接标准。设备遵循标准，就可以通过相应接口连接。

MCP 也是如此。我们可以把日历的能力封装成一个 MCP Server，支持 MCP 的 AI 应用则通过 MCP Client 与它通信。客户端按照协议发现能力、发起请求，Server 负责处理请求并返回结果。

一个 MCP Server 可以提供三类能力：

| 能力 | 作用 | 示例 |
|---|---|---|
| **Tools** | 执行操作 | 查询空闲时间、创建日程 |
| **Resources** | 提供数据和上下文 | 日历列表、日程详情 |
| **Prompts** | 提供提示模板 | 每周日程规划模板 |

这样一来，日历的能力就不必绑定在某一个 AI 应用里。只要客户端支持相应的 MCP 能力，就可以按统一方式接入。

当然，MCP 也有成本：需要配置和维护 Server，处理通信、认证授权和安全问题。如果只是应用内部的几个简单函数，直接使用 Tool 往往更轻量。

> **简单理解：MCP 解决的是 AI 应用如何标准化地连接外部能力。**

## 🧩 Tool、Skill、MCP 有什么区别？

把三个概念放在一起看，区别就比较清楚了。

| 对比维度 | Tool | Skill | MCP |
|---|---|---|---|
| **本质** | 功能接口 | 知识与工作流程 | 开放协议 |
| **核心问题** | 能做什么 | 怎么做好 | 怎么连接 |
| **主要内容** | 函数、参数、返回值 | 指令、知识、脚本、资源 | Tools、Resources、Prompts |
| **核心价值** | 扩展执行能力 | 沉淀专业经验 | 标准化接入与复用 |

再回到最初安排一周日程的场景。

当我们让 AI“查看下周的日历，按照我的习惯安排工作和生活，并创建日程”时：

- **Tool** 提供查询日历、创建日程、设置提醒等具体功能；
- **Skill** 告诉 AI 按照什么偏好和原则安排时间；
- **MCP** 让不同 AI 应用能够通过统一协议接入日历的相关能力。

这里有个容易混淆的地方：**MCP Server 可以提供 Tools，但 Tool 和 MCP 不是同一个概念。** Tool 是具体的功能，MCP 是客户端与服务端之间的交互协议。

三者可以组合使用，而不是互相替代。

---

## 💡 什么时候应该使用 MCP？

技术选型没有必要追求越复杂越好。

如果只是给一个 Agent 增加几个简单函数，直接使用 Tool 就够了；如果希望 AI 掌握专业知识，按照固定方法完成任务，Skill 更合适。

而当同一套业务能力需要被多个 AI 应用共享，或者企业希望以统一方式开放 CRM、ERP、OA、数据库等系统能力时，MCP 的价值就体现出来了。

它减少的是不同 AI 应用重复适配外部系统的工作，让业务能力有机会独立出来，被更多兼容的客户端复用。当然，实际能否复用，还取决于客户端支持情况、权限配置和服务端实现。

---

## ✍️ 写在最后

Tool、Skill 和 MCP 并不是三种互相竞争的技术，它们解决的是不同问题：

- **Tool：** 让 AI 拥有执行能力。
- **Skill：** 让 AI 掌握专业知识和工作方法。
- **MCP：** 让 AI 能够标准化地连接外部系统。

所以，为什么用 MCP，而不是 Skill、Tool？

不是因为 MCP 更高级，而是当 AI 应用越来越多、外部系统越来越复杂时，我们需要一种统一的连接方式。

**Tool 解决能力，Skill 沉淀经验，MCP 打通连接。**

理解它们各自的定位，比盲目选择某一种技术更加重要。
