# BM25 是什么？理解搜索系统里最经典的「关键词匹配」算法

最近在学习搜索和 RAG 的过程中，我重新了解了一个非常经典的方法：**BM25**。如果你接触过搜索引擎、信息检索，或者最近比较火的 RAG，大概率都会遇到两个词：**稀疏检索（Sparse Retrieval）** 和 **稠密检索（Dense Retrieval）**。

Dense Retrieval 我们现在比较熟悉，就是把文本转成 Embedding，然后通过向量相似度去找“语义上相近”的内容。而 BM25，基本可以看作 Sparse Retrieval 里最经典、最有代表性的算法之一。

简单来说：

> **BM25 做的事情，就是判断一篇文档和你的搜索关键词到底有多匹配。**

但它又不是简单地“看看关键词出现了几次”。它真正有意思的地方在于：**BM25 对“一个词出现多少次”“这个词有多稀有”“文档有多长”这几件事情，都做了更加合理的处理。** 理解了这几点，其实 BM25 就已经理解得差不多了。

这篇文章会先从一个最简单的关键词搜索说起，顺着三个问题一步步引出 BM25 的核心设计，最后再聊聊它在今天的搜索和 RAG 系统里扮演什么角色。

---

## 一、🔍 先从最简单的关键词搜索说起

假设我们有三篇文章：

| 文章 | 内容 |
|------|------|
| 文章 A | 苹果公司今天发布了新款 iPhone，苹果公司表示新产品将在下个月上市。 |
| 文章 B | 苹果是一种常见水果，苹果富含维生素和膳食纤维。 |
| 文章 C | 微软发布了新的人工智能产品。 |

现在用户搜索：

> 苹果公司

最简单的搜索方法是什么？可以直接数：**“苹果”和“公司”这两个词，在每篇文章里面出现了多少次。** 显然文章 A 的匹配程度最高。

这其实就是关键词检索最核心的思想：用户输入了一些词，我们去寻找包含这些词的文档。

这种表示方式通常非常“稀疏”——假设整个词表有 10 万个词，一篇文章可能只出现其中几百个，那么绝大多数位置都是 0。所以这一类方法通常被称为 **Sparse Retrieval，稀疏检索**。

但问题来了：如果只是简单地统计关键词出现次数，很快就会遇到几个问题。

---

## 二、❓ 问题一：一个词出现 100 次，真的比出现 10 次重要十倍吗？

假设我们搜索“人工智能”，有两篇文章：文章 A 中“人工智能”出现了 3 次，文章 B 中则出现了 100 次。如果单纯按照词频计算，那么文章 B 的相关性可能是文章 A 的几十倍，但现实显然不是这样。

一篇文章里，一个关键词出现 1 次和出现 0 次，区别很大；出现 5 次和出现 1 次，也有一定区别；但出现 100 次和出现 50 次，通常就没那么大区别了。换句话说：

> **关键词频率带来的收益应该逐渐递减，而不是无限线性增长。**

这就是 BM25 非常重要的一个设计：**Term Frequency Saturation，词频饱和**。你可以把它理解成——BM25 会奖励一个关键词在文档中多次出现，但这个奖励会越来越小，大致可以理解成：

| 出现次数 | 加分效果 |
|---------|---------|
| 0 次 | 0 分 |
| 1 次 | 明显加分 |
| 2 次 | 继续加分 |
| 5 次 | 还有提升 |
| 20 次 | 提升已经很有限 |
| 100 次 | 不会因此获得 100 倍的优势 |

这就比简单统计词频合理很多。

---

## 三、❓ 问题二：所有词的重要程度一样吗？

显然也不是。比如用户搜索：

> 如何使用 Python 训练神经网络

这里面“如何”“使用”这样的词，实际上并没有特别强的区分度，因为很多文档都会出现；但是“Python”“神经网络”这些词就重要得多。特别是如果某个词在整个文档库里非常少见，那么当它出现在一篇文章里时，它往往能够提供非常强的信息。

这就是信息检索里另一个非常经典的概念：**IDF，Inverse Document Frequency，逆文档频率**。它背后的思想非常直观：

> **一个词越稀有，搜索价值通常越高。**

举一个极端例子。假设我们有 100 万篇网页，不同词的出现情况和搜索价值差别非常大：

| 词 | 出现在多少篇文章中 | 搜索价值 |
|----|------------------|---------|
| “的” | 约 90 万 | 基本无法帮助筛选文档 |
| Transformer | 约 1 万 | 区分能力较强 |
| BM25 | 几千 | 搜索价值更高 |

所以 BM25 会给不同关键词不同的权重，粗略理解就是：

```text
非常常见的词 → 权重低
比较少见的词 → 权重高
非常稀有的词 → 权重更高
```

这也是 BM25 能比普通关键词计数效果好很多的重要原因。

---

## 四、❓ 问题三：长文章是不是天然更容易命中关键词？

还有一个很容易被忽略的问题。假设有两篇文章，都出现了 3 次 BM25：

| 文章 | 字数 | “BM25” 出现次数 |
|------|------|----------------|
| 文章 A | 200 字 | 3 次 |
| 文章 B | 2 万字 | 3 次 |

哪一篇和 BM25 更相关？很多情况下，很可能是文章 A。因为 200 字里出现 3 次 BM25，说明整篇文章大概率就是围绕这个主题展开；而一篇 2 万字的文章里出现 3 次 BM25，有可能只是在某个角落顺带提了一下。如果只是单纯统计词频，这两篇文章得分可能一样——甚至长文章天然会因为包含更多单词，更容易匹配用户 Query。

所以 BM25 还做了一件事情：**Document Length Normalization，文档长度归一化**。也就是说，BM25 会考虑一篇文档到底有多长，如果一篇文章特别长，那么关键词出现几次，不会被给予过高的权重。这实际上是在修正长文档天然占便宜的问题。

---

## 五、🧩 所以 BM25 到底做了什么？

到这里，我们其实已经可以不用公式理解 BM25 了。当用户输入一个 Query，比如“Python RAG 教程”，BM25 会分别看 Query 里的每一个词（Python、RAG、教程），然后针对每一个词，计算三个东西。

### 1. 这个词在当前文档里出现了多少次？

出现越多，一般说明越相关，但收益会逐渐饱和。

### 2. 这个词在整个文档库里有多稀有？

越稀有的词，信息量越高。比如“教程”可能很常见，“RAG”可能相对少见：

| Query 词 | 在文档库中的出现情况 | 权重 |
|---------|-------------------|------|
| 教程 | 很常见 | 较低 |
| RAG | 相对少见 | 较高 |

同样是 Query 里的词，RAG 的权重通常会比“教程”更高。

### 3. 当前文档是不是特别长？

如果文档特别长，BM25 会对词频做一定修正。

最后，把 Query 里每个关键词的分数加起来，就得到了 Query 和 Document 的 BM25 Score。分数越高，通常意味着关键词层面的相关性越强。

---

## 六、📐 如果一定要看公式，BM25 大概长这样

如果你还想更进一步，看看 BM25 在数学上到底怎么表达，它最常见的形式是这样的：

$$
\text{Score}(D,Q)=\sum_{q_i\in Q}\text{IDF}(q_i)\cdot\frac{f(q_i,D)\,(k_1+1)}{f(q_i,D)+k_1\left(1-b+b\cdot\frac{|D|}{\text{avgdl}}\right)}
$$

第一次看到可能会觉得复杂，但拆开来看，它其实就是前面几节内容的数学版：最外层的 $\sum$ 负责把 Query 里每个词的得分加起来，剩下三个部分正好对应第二节到第四节讲的三个思想。

**$\text{IDF}(q_i)$：这个词有多稀有。** 对应第三节讲的 IDF——词越稀有，这一项越大，这个词的权重就越高。

**$f(q_i,D)$：这个词在文档 D 里出现了多少次。** 也就是词频。有意思的是，它同时出现在分子和分母里：分子让它得分更高，分母又把它往回拉，一推一拉之间，收益就逐渐饱和了——这正是第二节讲的词频饱和。

**$|D|/\text{avgdl}$：文档的相对长度。** 当前文档长度除以整个语料库的平均长度。文档越长，这一项越大，词频带来的加分就会被“稀释”——这正是第四节讲的文档长度归一化。

所以这个公式看着唬人，其实就是在说：每个词的得分 = 稀有度 × 打折后的词频 × 长度修正。至于下一节要讲的 k1 和 b，就是控制“词频折扣”和“长度修正”这两个旋钮。

---

## 七、🎛️ 两个非常重要的参数：k1 和 b

上面的公式里还有两个参数：**k1** 和 **b**，它们分别控制词频饱和和文档长度归一化这两个机制。

### k1：控制词频饱和速度

k1 决定了一个关键词多出现几次，到底还能带来多少额外收益。k1 越小，词频越容易饱和——出现几次之后，再继续出现，收益就已经非常小；k1 越大，BM25 就越重视词频。实践中经常会看到类似 `k1 ≈ 1.2 ~ 2.0` 的取值，当然具体值还是要根据任务调优。

### b：控制文档长度归一化程度

b 决定了我们到底有多在意文档长度。当 `b = 0` 时，相当于完全不考虑文档长度；当 `b = 1` 时，则会进行比较完整的长度归一化。很多实现里默认会使用 `b ≈ 0.75`。

把两个参数放在一起看：

| 参数 | 控制什么 | 直观含义 | 典型值 |
|------|---------|---------|--------|
| k1 | 词频饱和速度 | 越小越容易饱和，越大越重视词频 | 1.2 ~ 2.0 |
| b | 文档长度归一化程度 | 越小越忽略长度，越大越在意长度 | 0.75 |

所以如果以后你看到 `BM25(k1=1.5, b=0.75)`，其实就可以理解成：这是在调节“词频影响”和“文档长度影响”这两个因素。

---

## 八、⚖️ BM25 和 TF-IDF 是什么关系？

说到 BM25，经常会顺便提到另一个经典算法：**TF-IDF**。它们其实有很深的关系。

TF-IDF 的核心思想是 `TF × IDF`：一个词在当前文档出现得越多，越重要；一个词在整个语料库越稀有，也越重要。这个思想本身非常经典。

但 TF-IDF 有一个比较明显的问题：**TF 通常增长得比较直接**。比如一个词出现 20 次，可能比出现 2 次获得非常大的权重。BM25 在这个基础上又进一步做了两个非常重要的改进：

| 维度 | TF-IDF | BM25 |
|------|--------|------|
| 词频 | 线性增长，出现 20 次的权重约是 2 次的 10 倍 | 词频饱和，收益逐渐递减 |
| 文档长度 | 完全不考虑 | 长度归一化，修正长文档偏差 |

所以可以非常粗略地理解为：

> **BM25 是一种更加成熟、更加符合真实搜索场景的 TF-IDF 类方法。**

当然严格从信息检索理论上，两者并不能简单画等号，但作为理解入口，这个类比是非常有帮助的。

---

## 九、⚠️ BM25 最大的问题：它“不懂语义”

看到这里，BM25 好像已经非常聪明了，但它有一个非常明显的限制：

> **BM25 本质上还是关键词匹配。**

比如用户搜索“如何提高大模型回答的准确性？”，而文档写的是“降低 LLM hallucination 的几种方法”。从人的角度看，两者显然高度相关，因为我们知道：大模型 ≈ LLM，回答不准确 ≈ hallucination。但 BM25 并不真正理解这个语义关系——如果 Query 和 Document 没有共享足够多的词，它的得分可能就不会很高。

这也是为什么后来 Embedding Search 会这么流行。Embedding 做的是另外一件事：

> **把文本映射到一个向量空间中，根据语义距离寻找相似内容。**

所以即使 Query 是“苹果手机”、Document 是“iPhone 16 使用体验”，没有完全相同的关键词，Embedding 模型仍然可能知道它们在语义上高度相关。

---

## 十、🤔 既然有了 Embedding，为什么 BM25 还没有消失？

这是一个非常有意思的问题。如果 Dense Retrieval 可以理解语义，那是不是直接用 Embedding 就好了？实际上并不是——BM25 到今天依然被大量使用。

原因在于：**关键词匹配和语义匹配，擅长解决的问题并不完全一样。** 比如用户搜索下面这些内容：

| 场景 | 例子 |
|------|------|
| 网络报错 | `ERR_CONNECTION_RESET` |
| 订单号 | `202608140031` |
| 产品版本 | `GPT-5.2` |
| 函数名 | `getUserById` |

这种 Query 最大的特点是什么？它们需要的是**精确匹配**。Embedding 有时候反而会把一些“语义差不多”的东西找出来，但用户真正想找的，可能就是这个字符串本身。BM25 在这种场景下往往非常强。

所以在现实系统里，一个非常常见的方案是 **Hybrid Search**，也就是 **BM25 + Vector Search**：一个负责关键词匹配，一个负责语义匹配，然后把两边的结果进行融合。

---

## 十一、🚀 这也是为什么 BM25 在 RAG 时代重新变得很重要

如果你最近在学习 RAG，就会发现很多系统并不是“用户问题 → Embedding → Vector Database → Top K”这么简单。实际生产环境里的 Retrieval Pipeline 往往会越来越复杂，比如：

```text
User Query
   ↓
Query Rewrite
   ↓
BM25 Retrieval
   +
Vector Retrieval
   ↓
Result Fusion
   ↓
Reranker
   ↓
Top K Documents
   ↓
LLM
```

BM25 在这里扮演的角色非常清楚：**负责找出“字面上高度匹配”的内容**；**Vector Search** 负责找出“语义上高度相关”的内容；**Reranker** 再进一步判断，到底哪些内容真正和用户的问题最相关。

所以 BM25 并不是一个已经被 Embedding 淘汰掉的老算法。恰恰相反，在今天很多搜索和 RAG 系统里，它依然是 Retrieval 层非常重要的一块。

---

## 十二、💡 我现在怎么理解 BM25？

如果让我现在用一句话解释 BM25，我可能会这样说：

> **BM25 是一个基于关键词的相关性排序算法，它会综合考虑关键词出现频率、关键词稀有程度以及文档长度，从而判断 Query 和 Document 在字面层面有多相关。**

再简单一点：**BM25 = 更聪明的关键词匹配。**

它不理解真正意义上的语义，但它非常擅长：**精确、稳定、高效地找到那些“确实包含你要找的东西”的文档。** 而这恰恰也是现代搜索系统里非常重要的一种能力。

所以当我们今天讨论 RAG、Embedding、Vector Database 的时候，也许不应该把 BM25 看成一个“上一代技术”。更加准确的理解应该是：**BM25 和 Embedding，其实是在解决检索问题的两个不同侧面**：

| | BM25 | Embedding |
|---|---|---|
| 关注 | 你写了什么词 | 你想表达什么意思 |
| 擅长 | 精确匹配、稳定高效 | 语义相近、同义表达 |
| 短板 | 不懂语义 | 对精确字符串不敏感 |

而一个好的搜索系统，往往两者都需要。
