# MinerU2.5：一个模型怎么干掉一整条 PDF 解析流水线

PDF 转 Markdown 现在是个挺刚需的活儿——训练大模型要喂干净的文本语料，做知识库、RAG 要把 PDF 拆成结构化内容，写论文笔记、整理资料也经常要把 PDF 里的表格公式抠出来复用。PDF 本身是给"看"设计的格式，不是给"读"设计的，怎么把它转成机器和人都好用的 Markdown，一直是个有真实需求、但没那么好解决的问题。

之前写过[一篇 MinerU Pipeline 的拆解](/2026/08/mineru-pdf-parsing-pipeline/)，介绍的是它怎么用 Layout Detection → OCR → Formula/Table Recognition → 后处理规则，一步步把 PDF 转成 Markdown。这套思路的问题也很直观：好几个专业模型串成一条链，Layout 判错一个框，后面全跟着错位；每个模型都要单独部署维护，后处理规则也越堆越多。

2025 年同一个团队发布的 **MinerU2.5**，换了个思路：**不用多个专业模型接力，只用一个 1.2B 参数的 VLM，让它自己跑两遍**。

两遍的分工很清楚：

> 🔭 **第一遍，看全局** —— 缩略图扫一眼整页，搞清楚"这里有什么、在哪、什么方向、按什么顺序读"。
> 🔬 **第二遍，看细节** —— 拿着第一遍标好的位置，去原图裁对应区域放大看，识别出具体内容。

同一个模型，只是喂给它的 Prompt 不一样，干的事就不一样。这篇文章只讲这两遍推理具体怎么分工、怎么衔接、怎么实现转换。

---

## 🔭 第一遍：版面分析——搞清楚"有什么、在哪"

这一步要回答的问题是：**这页文档有什么、在哪、什么方向、什么顺序。**

### 为什么先看缩略图，不看原图

直接在高分辨率原图上做版面分析，有两个绕不开的问题。一是 VLM 的 visual token 数量随像素平方增长，一页 A4 级别的文档轻松产生几千 tokens，页面里大片的空白边缘和行间距都在白白消耗算力。二是版面分析本身不需要看清每个字的笔画——只需要知道"这里有一块表""那里有一段正文"，缩略图完全够用。

MinerU2.5 把整页降采样到 **1036×1036 像素**。这个尺寸是权衡过的：太小会丢失细粒度元素的边界（比如小号字体、紧密排列的图注），太大又会落入 VLM 编码器的平方复杂度区间，划不来。用固定尺寸而不是保持原始宽高比，是因为固定尺寸下 bbox 的定位更稳定。

### 一次推理，四样东西一起出

模型用 Prompt `Layout Detection:` 看这张缩略图，输出页面上每个元素的结构化信息：

```
Box: [163  81 836 129]   Type: Table Caption   Orientation: up   Order: 1
Box: [169 138 831 250]   Type: Table           Orientation: up   Order: 2
Box: [162 264 486 471]   Type: Text            Orientation: up   Order: 3
...
```

跟 Pipeline 的 Layout Detection 对比一下差异就很清楚了。Pipeline 的检测模型只输出 label + bbox——"这是什么、在哪里"。阅读顺序要等后处理阶段靠几何规则（行高、缩进、对齐）去推断；旋转文本要单独判定方向后再校正。MinerU2.5 在第一遍就一步到位：阅读顺序直接编好号，旋转方向也标好了（up / down / left / right），下游模块不需要再猜。

类别也从 Pipeline 的十几种扩展到了 20+ 种——除了基础的 text、title、table、formula、image，还细分出了 code、algorithm、list、reference、header、footer、pagenumber、aside text 等。代码块和正文在视觉上很像，都是成段的文字，但语义完全不同，第一遍就把它们分开，第二遍识别时才能走对应正确的处理路径。

### 交给下一步

第一遍产出的是一份 bbox 列表。程序拿到列表后，对每一个 bbox 做三件事：

1. 从**原始高清图**（不是缩略图）按坐标裁出对应区域；
2. 如果旋转方向不是 up，顺手转正；
3. 根据类别，决定接下来用哪个 Prompt。

这是整个设计里最关键的一处衔接：高清像素只在裁剪后的局部区域进入后续推理，整页高清从头到尾不会完整地进入 VLM，从根本上避开了 token 爆炸。旋转校正也在这一步顺带完成——Pipeline 里"先判方向、再校正、再识别"的串行开销，被一句话省掉了。

## 🔬 第二遍：内容识别——搞清楚"具体是什么"

第一遍告诉你"这里有一块公式"，第二遍负责"这块公式具体是什么"。同一个模型，根据类别切不同 Prompt，输出不同格式的结果。

### 📄 文本：最直接的一条路

Prompt 用 `Text Recognition:`，输入是裁剪出的文字区域图片（原生分辨率），模型直接输出纯文本：

```
The results of the analyses of the uncertainty of the field data
and related assumptions are shown in Figs 13 and 14.
```

没有坐标、没有标签，输出即所得。这一点跟 Pipeline 不同——Pipeline 的文字来源要分两条路：扫描件跑 OCR 模型，数字 PDF 直接读文本层。MinerU2.5 统一走 VLM 识别，不管原文件是什么类型。

### 🧮 公式：先拆开，再拼回去

短公式直接进 `Formula Recognition:`，输出 LaTeX。但长公式和多行推导（比如 `align` 环境里那些对得整整齐齐的等号）直接整块识别很容易出问题——模型容易在结构上产生幻觉：漏一个等号对齐位、多一行、少一个 `\right`。

MinerU2.5 的方案叫 **ADR**（Atomic Decomposition and Recomposition，原子分解与重组），核心想法是把公式分成两类：

- **原子公式**：单个、不可再拆的语义单元——一个矩阵、一个分数、一个等式，2D 拓扑关系紧密，适合独立识别。
- **复合公式**：一组原子公式按特定对齐关系垂直排列的序列，典型的就是多行推导过程。

复合公式在识别前多走一步拆解：先用 Layout Detection Prompt 定位出里面每一行原子公式的 bbox，再把每一行独立裁出来，切到 Formula Recognition Prompt 做识别，最后按位置信息把结果拼回完整的公式块。

拆解和识别用的是同一个 MinerU2.5 模型，只是 Prompt 不同——先当"拆解器"，再当"识别器"。

例如一段包含多个公式的区域，最终输出的 LaTeX：

$$
\hat{F} = \operatorname{Concat}\left(\left[ F_{1}, F_{2}, \dots, F_{n} \right]\right) \tag{2}
$$

$$
M = \sigma \bigl( \mathrm{GELU}(\mathrm{BN}(\mathrm{Conv}_{gate}(\hat{F}))) \bigr) \tag{3}
$$

### 📊 表格：先用一种更紧凑的"中间语言"，再转成 HTML

做表格识别的 VLM 通常直接输出 HTML，但 HTML 对表格来说其实是"绕了一圈"——`<table>`、`<tr>`、`<td>`、`<thead>`、`<tbody>` 构成的是一棵层级树，跟表格的 2D 网格结构没有直接对应，模型得隐式学会"一个 `<tr>` 等于一行"这种映射。而且标签冗余度高，大表格的序列很容易超长，序列越长，VLM 生成时越容易出错。

MinerU2.5 的做法是让模型先输出一种专门为表格设计的中间表示（OTSL），这种表示里的标记直接对应表格的行、列、合并单元格，结构 token 种类比 HTML 少得多，序列也短得多，模型生成起来更稳。拿到这份中间结果后，再用一步确定性的规则转换，直接生成标准 HTML 表格。

整个表格处理流程是：第一遍出 bbox + 旋转方向 → 裁剪、旋转校正 → 模型识别出表格中间表示 → 规则转换成 HTML。

比如一张关于不同地点雨水化学成分的表格，最终转出来的 HTML 大致是这样（表头一行，下面按地点分组，其中有一行是跨列的分组标题）：

| Site | Cl | NO3 | SO4 | Na | Ca | K | Mg | NH4 | References |
|---|---|---|---|---|---|---|---|---|---|
| **Cl dominance sites** ||||||||||
| Comba | 109.8 | 12.1 | 23.3 | 86.8 | 43.4 | 4.8 | 15.1 | 13.2 | Present study |
| Alibagh | 236 | 9 | 36 | 220 | 46 | 5 | 64 | 8 | Naik et al. (2002) |

"Cl dominance sites"这一行在 HTML 里是一个跨 10 列的合并单元格（`colspan=10`），这种合并结构在中间表示里只需要几个简单标记就能表达，换成 HTML 直接生成反而容易出错——这正是先用中间表示、再转换的意义所在。

复杂度从"模型生成端"转移到了"规则明确的转换步骤"，结果更可控。

## 📐 跟 Pipeline 摆在一起看

| 环节 | MinerU Pipeline | MinerU2.5 |
|---|---|---|
| Layout | 专用检测模型（label + bbox） | VLM 看缩略图（label + bbox + 方向 + 顺序） |
| 文字 | OCR 模型 / 读 PDF 文本层（两套路） | VLM 第二遍统一识别 |
| 公式 | 专用公式模型 → LaTeX | 第二遍 + ADR 拆-合 |
| 表格 | 专用表格模型 → HTML | 第二遍 → 表格中间表示 → HTML |
| 阅读顺序 | 后处理靠几何规则推断 | 第一遍直接给编号 |
| 后处理 | 大量几何规则（框归属、段落合并等） | 极简，核心只剩表格格式转换 |

Pipeline 把复杂性分散在一堆专业模型和海量后处理规则里；MinerU2.5 把复杂性收回到一个 VLM 里，靠两次推理的分工和 Prompt 切换来组织整个流程。
