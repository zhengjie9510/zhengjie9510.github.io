# 如何构建有效的 Agent：Anthropic 的实践经验

最近读到 Anthropic 的一篇文章《Building effective agents》，把 Agent 的架构和落地方式讲得很清楚，值得分享给正在做 AI 应用的朋友。

Anthropic 与来自不同行业的数十个团队合作后发现，最成功的实现往往采用的是**简单、可组合的模式**，而不是复杂的框架或专用库。

## 什么是 Agent？

“Agent”这个词，并没有完全统一的定义。

有些人用它指能够长时间独立运行、调用各种工具完成复杂任务的全自主系统；也有人把按照预设工作流执行的系统叫作 Agent。

Anthropic 将这些实现统称为 **Agentic Systems**，但在架构上，明确区分了两类：

- **工作流（Workflows）**：由预先定义好的代码路径，组织大模型和工具的执行。
- **Agent**：由大模型动态决定执行过程和工具使用方式，自主控制如何完成任务。

两者的关键区别在于：执行路径是由代码预先确定，还是由模型根据任务动态决定。

## 什么时候该用 Agent，什么时候不该用？

构建大模型应用时，可以先从最简单的可行方案开始，确有需要时再增加复杂度。有些任务，根本不需要 Agent。

**Agent 系统通常是在用更高的延迟和成本，换取更好的任务表现。** 这样的取舍是否值得，需要结合具体场景判断。

如果任务定义清晰，工作流能够提供更强的可预测性和一致性。如果需要在大量任务中灵活应对不同情况，并由模型自主做出决策，Agent 才更有优势。

而对不少应用来说，把单次模型调用做好，配合检索和上下文示例，就已经足够了。

## 五种常见的工作流

任务如何拆分、调用如何组织，决定了工作流的结构。下面五种模式各有适用场景，可以按需选择和组合。

### 工作流一：提示链（Prompt Chaining）

提示链把一个任务拆成一系列连续步骤，每次模型调用处理上一步的输出。

中间还可以加入程序化检查，确认上一步的结果符合要求，再继续执行。

**什么时候适合用？**

当一个任务能够清晰地拆成若干固定子任务时，提示链就很合适。每次调用只处理一个更简单的任务，以更长的执行时间换取更高的准确性。

**典型例子：**

- 先生成营销文案，再翻译成另一种语言。
- 先写文档大纲，检查大纲是否满足要求，再根据通过检查的大纲写正文。

### 工作流二：路由（Routing）

路由先对输入进行分类，再交给相应的专门流程处理。

这样可以把不同问题分开，为每类任务设计更有针对性的 Prompt。如果所有输入都挤在同一套处理逻辑里，对一类输入的优化，可能反而损害另一类输入的效果。

**什么时候适合用？**

当输入可以准确分类，而且不同类别适合采用不同的处理方式时，路由就很有效。分类本身可以交给大模型，也可以使用传统的分类模型或算法。

**典型例子：**

- 将一般咨询、退款请求、技术支持等不同类型的客服问题，分配给不同的下游流程、Prompt 和工具。
- 将简单、常见的问题交给 Claude Haiku 4.5 这类更小、成本更低的模型；将困难、不常见的问题交给 Claude Sonnet 4.5 这类能力更强的模型，在效果和成本之间做权衡。

### 工作流三：并行化（Parallelization）

有些任务可以让多个模型调用同时执行，再用程序汇总结果。

并行化主要有两种形式：

- **任务拆分（Sectioning）**：把任务分成彼此独立的子任务，并行执行。
- **投票（Voting）**：对同一个任务执行多次，获得不同的输出，再综合判断。

**什么时候适合用？**

一类情况是子任务相互独立，可以通过并行缩短执行时间；另一类情况是需要多个视角或多次尝试，提高结果的可信度。

对于需要同时考虑多个因素的复杂任务，把每个因素交给单独一次模型调用，通常能让模型更专注，从而改善表现。

**任务拆分的例子：**

- 一个模型实例负责处理用户请求，另一个实例负责检查是否存在不当内容或请求。相比让同一次调用兼顾安全检查和核心回答，这种分工通常表现更好。
- 自动评估模型表现时，让不同的模型调用分别评价同一输出的不同方面。

**投票的例子：**

- 审查代码漏洞时，用多个不同的 Prompt 分别审查，发现问题就标记出来。
- 判断内容是否不当时，用不同的 Prompt 检查不同方面，或者调整投票通过的阈值，在误报和漏报之间取舍。

### 工作流四：编排者与工作者（Orchestrator-Workers）

在这种工作流里，一个大模型担任编排者，动态拆解任务，将子任务分配给其他模型，再汇总结果。

**什么时候适合用？**

对于事先难以确定子任务的复杂问题，这种方式很合适。

比如修改代码，需要动几个文件、每个文件具体怎么改，往往取决于这一次的任务，无法提前写死。

它在结构上看起来和并行化相似，但有一个关键区别：

**并行化的子任务通常是预先确定的；编排者与工作者模式中的子任务，则由编排者根据当前输入动态决定。**

**典型例子：**

- 需要根据任务，对多个文件进行复杂修改的编程产品。
- 需要从多个来源收集资料、分析并筛选相关信息的搜索任务。

### 工作流五：评估与优化（Evaluator-Optimizer）

这种工作流中，一次模型调用负责生成结果，另一次负责评价并提出反馈，再根据反馈修改，形成迭代循环。

**什么时候适合用？**

当评价标准明确，而且反复修改能够带来可衡量的改善时，这种方式就很有效。

可以用两个信号判断是否适合：

1. 人类给出明确反馈后，模型的回答能够明显变好。
2. 模型本身也有能力提供这样的反馈。

这个过程类似于人类写作：先完成初稿，再根据评价反复修改，直到得到更成熟的作品。

**典型例子：**

- 文学翻译中，负责翻译的模型可能没有充分处理某些细微含义，而评估模型能够指出这些问题并提出建议。
- 复杂搜索任务需要多轮检索和分析，评估模型负责判断现有资料是否充分，以及是否需要继续搜索。

## 什么时候需要自主 Agent？

当任务的执行路径无法提前确定时，就需要考虑让模型获得更多自主性。理解复杂输入、推理与规划、可靠使用工具，以及从错误中恢复，都是支撑这种自主性的关键能力。

Agent 的任务可以始于用户的一条指令，也可以通过与用户对话逐步明确。

任务明确后，Agent 自主规划并执行；必要时，再向用户索取信息或请求判断。

执行时，一个关键要求是：**每一步都要从环境中获得真实反馈，用来判断进展。** 这些反馈可以是工具调用的结果，也可以是代码实际运行的结果。

在预设检查点，或者遇到阻碍时，Agent 可以暂停，等待人的反馈。任务通常在完成后结束，也可以设置最大迭代次数等停止条件，确保过程可控。

Agent 能处理复杂任务，但实现本身往往并不复杂：通常就是大模型根据环境反馈，在一个循环里不断使用工具。

这个循环能否可靠运行，很大程度上取决于工具及其文档是否设计清楚。

**什么时候适合用？**

如果问题是开放式的，所需步骤难以提前预测，也无法用代码写死执行路径，就适合考虑 Agent。

模型可能需要连续运行很多轮，因此必须对它的决策能力有一定信任。在可信环境里，Agent 的自主性有利于规模化处理任务。

但自主性也意味着更高的成本，以及错误逐步累积的可能。Anthropic 建议在沙箱环境中充分测试，并配备适当的防护措施。

## 这些模式可以组合，也可以按需调整

上面的模式都可以根据实际场景调整和组合，不必当作固定模板照搬。

和其他大模型功能一样，关键在于衡量效果，并据此迭代实现。

**只有在复杂度确实能改善结果时，才值得把它加进来。**

从简单的 Prompt 开始，通过全面的评估不断优化；当简单方案确实不够用时，再引入多步骤的 Agent 系统。

Anthropic 将自己的实现原则归纳为三点：

1. **保持设计简单。**
2. **重视透明度，明确展示 Agent 的规划步骤。**
3. **认真打磨 Agent 与计算机之间的接口（ACI），通过完善的工具文档和测试提高可靠性。**

这些原则最终都指向同一个目标：让系统满足实际需求，同时保持可靠、易维护。

## 工具也需要 Prompt Engineering

无论采用哪一种 Agent 架构，工具通常都是重要组成部分。

以 Claude 为例，开发者通过 API 定义工具的准确结构和用途，让模型能够与外部服务及 API 交互。当模型打算调用工具时，会在响应中返回工具调用块（tool use block）。

**工具的定义和说明，值得像整体 Prompt 一样认真打磨。**

### 同一个动作，表示方式也会影响模型表现

同一个操作，往往有不同的表达方式。

比如修改文件，可以输出 diff，也可以重写整个文件；返回结构化内容时，可以把代码放进 Markdown，也可以放进 JSON。

从软件工程角度看，这些表示形式通常可以无损转换。但对大模型来说，不同格式的生成难度并不一样。

例如，生成 diff 时，模型需要先在差异块的头部写出相关行号和行数，再生成具体的修改内容。相比之下，把代码放进 JSON，又会增加换行和引号的转义负担。

Anthropic 对工具格式的建议是：

- 给模型留出足够的推理空间，避免它过早生成某些内容，导致后续难以保持一致。
- 尽量采用模型在训练中常见、容易生成的格式。
- 减少额外的格式负担，例如精确统计数千行代码，或者对生成的代码逐一做字符串转义。

### 像设计人机界面一样，设计 Agent 的工具接口

一个实用的原则是：设计 Agent 与计算机的接口（ACI），也应该像设计人机交互界面（HCI）一样用心。

具体可以从四个方面入手。

**第一，站在模型的角度看工具。**

只看描述和参数，是否马上就知道怎么用？如果人都需要琢磨半天，模型大概率也会困惑。

好的工具定义通常应该包含使用示例、边界情况、输入格式要求，以及它和其他工具之间的明确区别。

**第二，把参数名称和说明写清楚。**

可以把它当成给团队里一位初级开发者写函数文档。当系统里有很多相似工具时，清楚的命名和说明尤其重要。

**第三，测试模型实际上会怎样使用工具。**

在 Workbench 等测试环境中运行大量示例输入，观察模型会犯哪些错误，再根据这些错误迭代工具设计。

**第四，让工具本身更不容易被用错。**

这就是防错设计（Poka-yoke）：通过修改参数和接口，让错误更难发生。

Anthropic 分享了一个很具体的例子。

在构建用于 SWE-bench 的 Agent 时，他们花在优化工具上的时间，实际上比优化整体 Prompt 还多。

其中一个问题是：Agent 的工作目录离开项目根目录后，使用相对路径容易出错。他们把工具改为始终要求绝对路径，模型随后便能正确使用，不再出现这类路径错误。

这个例子也提醒我们：**Agent 的可靠性，既取决于模型能力，也取决于交到它手里的工具是否清楚、好用。**
