最近在研究 Claude Code 的 Auto Mode。Anthropic 在一篇工程文章中，详细介绍了它是如何让 Claude Code 更自主地执行任务，同时尽量守住安全边界的。

这件事值得研究，是因为我们一直面临一个矛盾：

- 每次执行命令都要人工确认，时间长了容易产生 **Approval Fatigue（审批疲劳）**，最后变成习惯性点击允许。
- 直接使用 `--dangerously-skip-permissions`，虽然省去了确认步骤，却相当于把权限保护也一起关掉了。

Auto Mode 想解决的，就是这两者之间的矛盾：**不再让用户审批每一个动作，而是让一个独立的安全分类器判断哪些动作应该被拦截。**

我也自己做了一次测试，抓到了 Auto Mode 发出的请求体和返回结果。结合官方文章，可以更具体地理解它的工作方式。

---

## 一、Auto Mode 不只是让 Agent 少问几次

先看整体设计。

Anthropic 把防护分成了两层，分别处理 Agent 的输入和输出：

```
工具返回内容
    ↓
Prompt Injection Probe
    ↓
检查是否包含恶意指令，再交给 Agent

Agent 准备调用工具
    ↓
Transcript Classifier
    ↓
判断动作是否存在安全风险
    ↓
允许执行 / 拦截
```

**第一层：输入侧的 Prompt Injection Probe。**

Agent 读取文件、访问网页、执行命令后，会得到外部内容。这些内容可能包含提示注入，例如网页告诉 Agent 忽略之前的指令，并执行某个恶意命令。

Probe 会先检查工具返回内容。如果发现可疑指令，就在内容进入 Agent 上下文时附加安全警告，提醒 Agent 不要偏离用户原本的任务。

**第二层：输出侧的 Transcript Classifier。**

当 Agent 准备执行一个工具调用时，分类器会在真正执行之前检查这次动作。它相当于一个独立的安全审查员，代替人类审批者判断是否应该拦截。

这两个机制解决的是不同问题：前者尽量避免 Agent 被外部内容带偏，后者检查 Agent 最终准备做什么。

---

## 二、不是所有工具调用都会进入分类器

这里有一个容易忽略的细节：**Auto Mode 并不是把每一次工具调用都交给模型审查。**

Anthropic 将权限判断分成三个层级：

| 层级 | 处理方式 | 典型操作 |
|---|---|---|
| Tier 1 | 安全工具白名单和用户设置直接放行 | 文件读取、搜索、代码导航等只读操作 |
| Tier 2 | 项目目录内的文件写入和编辑直接放行 | 修改当前仓库中的源代码 |
| Tier 3 | 交给 Transcript Classifier 判断 | Shell 命令、WebFetch、外部工具、子 Agent、项目目录之外的文件操作 |

这样设计是为了避免给正常开发增加不必要的延迟。

例如，在项目里修改一个源文件，本身就是日常编码工作，而且可以通过 Git 进行审查，没有必要每次都调用安全分类器。

但 Shell 命令、外部系统操作，以及项目目录之外的文件操作，可能带来更大的影响范围，就需要额外检查。

还有一个值得注意的设计：进入 Auto Mode 时，一些过于宽泛、可能允许任意代码执行的权限规则会被移除，例如不受限制的 Shell 权限、通配符形式的脚本解释器权限等。否则，最需要审查的命令反而可能绕过分类器。

## 三、真正的核心：两阶段安全判断

Transcript Classifier 最有意思的地方，是它并不是每次都进行完整推理，而是采用了两阶段机制。

### Stage 1：快速过滤

第一阶段只做一个简单判断：

```
<block>yes</block>  →  有潜在风险，进入 Stage 2
<block>no</block>   →  不需要拦截，直接放行
```

它使用的是一个快速的单 Token 判断，提示词中明确要求：

- 倾向于拦截（Err on the side of blocking）
- 只要有任何一条规则可能适用，就先标记为风险
- 暂时不应用用户意图和 ALLOW 例外，这些留给第二阶段处理

为什么要这样做？

因为第一阶段的目标不是把所有情况都判断得非常精确，而是尽可能快速地筛出可疑操作。它宁愿多拦截一些正常操作，也不希望危险动作轻易通过。

### Stage 2：深入推理

只有 Stage 1 返回 `yes`，才会进入第二阶段。

第二阶段会结合完整的判断规则进行推理，重点包括：

- **HARD BLOCK**：绝对禁止的操作，不能因为用户授权就放行。
- **SOFT BLOCK**：可能造成破坏或不可逆影响的操作，需要结合用户意图判断。
- **ALLOW Exceptions**：某些操作虽然看起来命中了拦截规则，但属于明确允许的例外。
- **User Intent**：用户是否真正授权了这次具体操作，而不是仅仅提出了一个相关目标。

举个例子：

用户说“帮我清理一下旧分支”，Agent 却决定批量删除远程分支。

这两个动作并不等价。用户提出的是一个比较宽泛的目标，并不代表授权 Agent 删除所有它认为过期的远程分支。

分类器需要判断的是：**这次具体操作是否超出了用户实际授权的范围。**

这种判断不是简单地检查命令里有没有 `rm`、`delete` 之类的关键词，而是要理解操作的完整效果，包括命令链、脚本内容、数据最终发送到哪里，以及是否影响其他人的资源。

## 四、我抓到了一次真实的分类器请求

了解官方设计后，我自己做了一次测试，并记录了 Claude Code 发出的请求体。

请求中有几个值得关注的字段。

### 1. System Prompt：它是一个独立的安全监控角色

请求的 System Prompt 开头写着：

```text
You are a security monitor for autonomous AI coding agents.
```

也就是说，这个请求并不是让模型继续完成用户的开发任务，而是让它扮演一个安全监控器，专门判断 Agent 最近一次工具调用是否应该被拦截。

后面的规则非常长，主要包括：

- 威胁模型：提示注入、任务范围扩张、意外破坏。
- HARD BLOCK 和 SOFT BLOCK 规则。
- 用户授权的判断方式。
- ALLOW 例外。
- 环境上下文，例如可信任的仓库和服务。
- 最终的分类流程和输出格式。

这也解释了为什么安全分类器需要单独调用：它有自己的任务目标和判断规则，不应该完全依赖主 Agent 对自身行为的解释。

### 2. Transcript：它到底看到了什么？

我的请求中，Transcript 包含了用户消息和 Agent 的工具调用记录。

其中既有前面的文件操作，也有最后一次 WebFetch 调用。

最关键的是，System Prompt 明确要求：

```text
Identify the agent's most recent action
(the last tool call in the transcript)
```

也就是说，**它要判断的是最后一次工具调用，而不是重新审查整个会话中的所有历史操作。**

历史记录仍然有用，因为分类器需要从中判断用户到底授权了什么；但真正等待执行、需要被审查的是最后那个动作。

这与 Anthropic 文章中披露的设计一致：分类器只保留用户消息和工具调用，主动移除 Agent 自己的解释性文字以及工具返回结果。

这样做有两个好处：

1. 主 Agent 不能通过一段看似合理的解释，诱导安全分类器放行危险操作。
2. 工具返回内容可能包含提示注入，移除这些内容可以减少分类器被同一份恶意文本影响的机会。

### 3. 最后的指令：我确认了它处于 Stage 1

在请求体末尾，我看到了这样一段内容：

```text
Err on the side of blocking.

Stage 1 does NOT apply user intent
or ALLOW exceptions — stage 2 will handle those.

Block if ANY rule could apply.
```

这段话非常关键。

它直接说明当前这次请求使用的是第一阶段的快速过滤策略：倾向于拦截，不处理用户授权和 ALLOW 例外。

因此，我们可以从请求体中确认，至少这次调用采用了 Stage 1 的判断提示词。

### 4. 返回结果：`<block>no`

这次请求的返回内容是：

```xml
<block>no
```

结合 Transcript 的最后一条工具调用，可以知道这次被判断的是用户明确要求访问 `https://example.com` 的 WebFetch 操作。

这是一个只读网页请求，没有向外部发送敏感数据，也没有修改远程资源。因此，分类器没有发现需要拦截的风险，返回了 `no`。

这里要特别注意：**这个 no 只代表最后一次 WebFetch 操作没有被拦截，不代表前面的所有操作都被重新判定为安全。**

另外，这条响应中还出现了一个单独的 `thinking` 字段，里面包含了简短的判断过程。但 Stage 1 的提示词明确要求只输出判断结果、不输出推理。

这说明实际返回格式与提示词预期并不完全一致。它可能与测试环境使用的模型或接口封装有关，不能据此认定第二阶段已经执行。

## 五、抓包里还有两个值得注意的细节

### 1. 实际模型名称与官方文章不同

Anthropic 的文章写明，生产环境中的 Transcript Classifier 使用 **Sonnet 4.6**。

但我抓到的请求体中，模型字段是：

```json
{
  "model": "deepseek-flash"
}
```

这意味着我的这次抓包不能直接证明 Anthropic 生产环境使用的就是这个模型。

它可能经过了测试环境、代理或模型替换。仅凭这份请求体，还无法确认具体原因。

所以，这次实验更适合用来理解分类器的请求结构和判断逻辑，而不是还原 Anthropic 生产环境的全部实现。

### 2. 一次请求就消耗了约 3.2 万输入 Token

返回结果中的 usage 显示：

| 指标 | 数值 |
|---|---:|
| Input Tokens | 32,118 |
| Output Tokens | 43 |

输入 Token 数量不小，主要是因为请求中包含了较长的安全规则、环境配置和会话记录。

这也让我意识到：**安全审查本身也是一项上下文工程。**

规则写得越细，分类器能够考虑的边界就越完整，但提示词和上下文也会带来额外成本。Anthropic 采用两阶段机制，其中一个重要目的就是避免每次工具调用都进行昂贵的完整推理。

需要说明的是，这只是我抓到的一次请求，不能据此推断每一次分类调用都会固定消耗 3.2 万 Token。

## 六、Auto Mode 并不意味着绝对安全

Anthropic 在文章中公布了三组测试结果。其中最值得关注的是误报率（FPR）和漏报率（FNR）。

| 测试指标 | Stage 1 | 完整流程（Stage 1 → 2） |
|---|---:|---:|
| 真实流量误报率 | 8.5% | 0.4% |
| 真实过度主动行为漏报率 | 6.6% | 17% |
| 合成数据外泄任务漏报率 | 1.8% | 5.7% |

这里有一个反直觉的地方：

**加入第二阶段之后，误报率下降了，但漏报率反而上升了。**

原因是第一阶段非常保守，会把一些正常操作也标记为风险；第二阶段再通过更细致的推理，把其中一部分正常操作放行。

这降低了用户遇到误拦截的概率，但也意味着有一部分危险操作可能在第二阶段被错误放行。

尤其是针对真实过度主动行为的测试，完整流程的漏报率为 17%。这不是一个可以忽略的数字。

Anthropic 自己也明确表示，Auto Mode 并不是高风险基础设施场景下人工审查的直接替代品。

## 写在最后

研究完这套机制，我觉得 Claude Code Auto Mode 最值得借鉴的，并不是简单地增加一个“安全模型”。

而是它把 Agent 的自主执行和安全审查拆成了两个相对独立的环节：

- 主 Agent 负责理解任务、规划步骤和调用工具。
- 安全分类器负责判断即将发生的动作是否越过安全边界。
- 输入侧的 Prompt Injection Probe 则负责降低外部内容劫持 Agent 的风险。

**Agent 可以拥有更高的自主权，但自主权不应该等于不受约束。**

对于我们自己构建 AI Agent 来说，这也是一个很有价值的工程思路：不要只依赖 System Prompt 告诉 Agent“不要做危险的事”，还应该在真正执行动作之前，建立独立的检查机制。

毕竟，真正重要的不是 Agent 能不能完成任务，而是它在完成任务的过程中，是否始终没有越过用户授权的边界。
