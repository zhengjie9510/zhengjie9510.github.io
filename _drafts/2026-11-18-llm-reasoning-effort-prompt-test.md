接入推理模型后，一个常见的问题是：答案还没出来，模型已经思考了几十秒。

复杂问题多分析几步有价值，但写总结、做简单计算也要等很久，就会影响使用体验。我们用 Qwen3.8-27B
做了一组测试，想弄清楚两件事：原生的思考强度参数是怎么控制的？自己再加一句“不要过度思考”，能不能进一步缩短等待？

我们既记录模型多久开始回答、多久答完，也记录它在回答前生成了多少思考内容。

先说结果：在这批任务中，**low + 简短思考提示词的平均耗时最低**，平均思考1.53秒，正文平均在1.74秒开始出现。相比单独使用
low，思考时间减少约36%。

这回答了“怎样更快”，但还没有回答“怎样更好”。本次没有系统评估各组答案质量，下面的比较主要围绕等待时间展开。

## 1. low、medium、xhigh，实际上控制了什么？

通过 OpenAI 兼容接口调用 Qwen3.8-27B，可以设置：

```python
reasoning_effort = "low"
```

Qwen3.8-27B 支持 `low`、`medium` 和 `xhigh` 三个级别，官方模板默认使用
`xhigh`。[来源：官方模型说明](https://huggingface.co/Qwen/Qwen3.8-27B)

在这个模型中，参数的作用方式很直接：**系统根据你选择的档位，在发给模型的内容里加上一段指令。** 聊天模板就是负责组织这些输入内容的规则。

下面是模板中两段完整指令的中文翻译。为方便理解，展示的是译文，实际官方模板使用英文。

### low：明确要求简短思考

> 思考强度设置为 low。保持你的思考简短且聚焦，直接得出结论，不要进行不必要的展开。

### medium：不额外加入强度指令

**medium 不会额外加入一段“中等强度提示词”。** 模型仍然会思考，只是没有收到 low 或 xhigh 那样的额外要求。

所以，“medium 不加入额外指令”和“不传 reasoning_effort”并不是同一件事：不传时，官方模板会默认选择 xhigh。

### xhigh：明确要求仔细分析和验证

> 思考强度设置为 xhigh。请仔细思考整个任务，验证关键假设，考虑合理的替代方案，并优先确保最终答案的正确性、一致性和清晰度。

需要注意，这些是 Qwen3.8-27B 官方模板的具体实现，不能直接推广为所有推理模型的实现方式，但具有一定的参考价值。

### 这些指令如何进入模型？

比如，你选择 low，又写了一段自己的系统提示词，服务端会先把“简短思考”的指令放在前面，再接上你的提示词和用户问题，整理后发给模型。

```text
选择思考档位 → 模板加入对应指令 → 拼接你写的提示词和问题 → 发给模型
```

官方模板中，强度指令与现有 system
内容的拼接位置在第75—85行。[来源：system 消息拼接逻辑](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/chat_template.jinja#L75-L85)

整个过程发生在模型开始生成之前，无需修改模型本身。

可以把这些档位理解为对模型的要求：“尽量简短”或“仔细分析”。模型最终想多久，还会受到题目难度和其他提示词影响，并没有一个固定长度。

## 2. 已经设置 low，再加一句提示词有用吗？

既然 low 本身就在要求简短思考，再强调一次，会不会有用？我们在三个档位下，都额外测试了下面这句系统提示词（system）：

```text
请不要过度思考，尽量简短思考，直接给出符合要求的答案。
```

调用时，把这句话放进 system 消息，同时设置 `reasoning_effort="low"`。下面只展示与本文有关的部分：

```python
response = client.chat.completions.create(
  model="qwen38-27b",
  messages=[
    {
      "role": "system",
      "content": "请不要过度思考，尽量简短思考，直接给出符合要求的答案。",
    },
    {"role": "user", "content": "请根据以下材料写一份项目复盘……"},
  ],
  reasoning_effort="low",
)
```

按官方模板，low + prompt 的最终 system 内容可以理解为下面两段的组合，其中第一段实际为英文：

```text
思考强度设置为 low。保持你的思考简短且聚焦，直接得出结论，不要进行不必要的展开。

请不要过度思考，尽量简短思考，直接给出符合要求的答案。
```

medium + prompt 则只有我们自己加入的那段要求；xhigh + prompt 会同时包含充分分析和简短思考两类要求。这些要求最终怎样共同影响输出，需要用实际任务测试。

## 3. 用六组实验比较等待时间

实验包含六种组合：low、medium、xhigh，以及三者分别搭配上述提示词。下文表格中的“+ prompt”，就表示额外加入了这句话。

每组使用相同的三类任务：技术博客、简单数学题、项目复盘。每道题重复5次，每组15次，六组共90次生成请求。

所有组使用相同题目、相同顺序，逐次执行，控制生成随机性的采样参数也保持一致，但不固定随机种子（seed）。测试前先让服务运行起来，并关闭前缀缓存，尽量减少服务刚启动和重复输入缓存对耗时的影响。

先对每类任务的正常完成请求计算均值，再对三类任务等权平均，得到下面的结果。

每组只有15次请求，下面展示的是这批样本的平均表现；由于没有展示波动范围，细小差距不宜解读为稳定优势。“正常完成”仅表示请求生成了完整正文，不代表答案正确或质量达标。

### 时间表现

“正文等待”关注的是读者体验：要等多久才能看到回答正文；“总耗时”则要等到整个回答生成结束。两者都包含回答前的思考阶段，因此不能与“思考耗时”相加。

| 设置             | 平均思考耗时 | 平均正文等待 | 平均总耗时 |  正常完成 |
|------------------|-------------:|-------------:|-----------:|----------:|
| low              |       2.37秒 |       2.63秒 |     8.76秒 |     15/15 |
| medium           |       3.47秒 |       3.67秒 |    10.20秒 |     15/15 |
| xhigh            |      33.80秒 |      34.00秒 |    38.23秒 |     15/15 |
| **low + prompt** |   **1.53秒** |   **1.74秒** | **7.78秒** | **15/15** |
| medium + prompt  |       1.59秒 |       1.79秒 |     8.30秒 |     15/15 |
| xhigh + prompt   |       4.52秒 |       4.72秒 |    10.62秒 |     14/15 |

xhigh + prompt 有一次请求耗时92.50秒，最终没有生成正文。该次未计入成功请求的均值；计入失败尝试后，这组复盘任务每次尝试的平均耗时为30.55秒。因此，表中的成功均值不能代表每次调用的实际成本。

### Token 量与生成速度

Token 是模型处理和生成文字的计量单位，可以粗略理解为文本长度，但不等于字数。看这张表，重点比较“思考Token”和“输出速度”：前者反映模型生成了多少思考内容，后者反映每秒生成多少内容。

| 设置             | 总输出Token | 思考Token¹ | 正文Token¹ | 输出速度（Token/s） | 思考速度¹（Token/s） |
|------------------|------------:|-----------:|-----------:|--------------------:|---------------------:|
| low              |      699.73 |     221.27 |     476.33 |               85.78 |                92.31 |
| medium           |      814.93 |     315.27 |     497.27 |               84.57 |                93.11 |
| xhigh            |     3154.27 |    2767.33 |     383.67 |               84.58 |                82.33 |
| **low + prompt** |  **599.87** | **143.40** |     454.40 |               84.35 |                94.21 |
| medium + prompt  |      627.33 |     144.20 |     481.07 |               82.41 |                91.35 |
| xhigh + prompt   |      799.85 |     356.88 |     440.80 |               81.34 |                81.98 |

¹ 总输出Token来自生成响应的usage。服务端未提供独立思考Token统计，思考和正文使用同模型tokenizer重新计数，因此属于估算，分项之和可能与总输出略有差异。

输出速度是每次请求“总输出Token / 首末可见内容间隔”的速率，再按任务平均，不是批量并发吞吐量。思考阶段计时同样受流式分块和缓冲影响。

## 4. 更快，主要是因为思考内容变少了

**第一，在这批样本中，low 比 medium 的平均思考时间更短。** 从3.47秒降至2.37秒，减少约32%。

**第二，自己加 prompt 仍有收益。** low 加 prompt 后，思考时间从2.37秒降至1.53秒，减少约36%；medium 加 prompt
后，从3.47秒降至1.59秒，减少约54%。

这说明原生参数之外，场景提示词仍然能继续影响模型行为。

**第三，加 prompt 后，low 和 medium 已经很接近。** 两者的平均思考时间只差约0.06秒，思考Token约为143和144，不能仅凭这点差距宣称存在稳定优势。

**第四，模型更早开始回答，主要是因为生成的思考内容少了。** low 加 prompt 前后，每秒生成的内容基本相当，约为86和84个Token；但思考内容从约221个Token降到143个Token，因此更早进入正文。就像写字速度差不多，少写几段，就能更早写完。

**第五，平均更快，仍可能偶发长时间等待。** xhigh + prompt 中出现过一次92.50秒且没有正文的请求。评估使用体验时，除了均值，也要关注这样的失败尝试。

## 5. 最快的组合，还需要过质量这一关

在本次测试的六组配置中，**low + 简短思考提示词的平均思考耗时、正文等待和总耗时最低**。如果你的任务类似，可以把它作为降低延迟的候选配置，用自己的题目继续验证。

但“延迟最低”不等于“质量最好”。实验中仍发现了材料之外的事实补充和算术错误。简单数学题也不足以代表复杂推理能力，不能据此判断高强度对所有任务都没有价值。

下一步需要把同一道题在不同配置下的答案放在一起，比较事实准确性、计算正确率和要求完成度，再结合等待时间做选择。当前数据只能说明哪组平均最快，还不足以判断哪组最好。

对接入推理模型的人来说，这次测试提供了一个值得尝试的方向：设置思考强度后，仍可以加入符合场景的简短思考要求。在本次 low 和
medium 的测试中，这一步进一步缩短了等待；能否用于你的业务，还要看节省的时间是否伴随可接受的答案质量。
